# Filesystem security follow-up — 2026-09-25

Follow-up to [the previous review](SECURITY-2026-09-24.md), under the same trusted,
single-user, loopback-only deployment model.

## Findings fixed

| Finding | Impact and prerequisite | Change |
| --- | --- | --- |
| Worktree carry-over followed source and destination links | A pre-existing symlink or Windows junction could copy a file from outside the repository, or write a copied file outside the worktree. Requires a link in a configured carry-over path. | Check the source and destination paths for links. Preserve existing destination entries, including dangling links, and copy files exclusively so an existing destination is never overwritten. Intentional directory links created by carry-over still work on repeat runs. |
| Static serving followed links | A link planted in the built web directory could expose files outside that directory over the local HTTP server. | Check the build directory, requested file and fallback index for links before serving; reject linked paths with HTTP 404. |
| Artifact listing followed a linked root | Downloads already rejected links, but listing an artifact directory replaced with a junction exposed external filenames, sizes and timestamps. | Apply the same link checks to the directory and listed file paths, returning HTTP 400 for unsafe paths. |
| Predictable temporary files were opened for overwrite | A pre-existing hard link or symlink at `secrets.json.tmp` could redirect credential writes into another file. An existing temporary file could also retain broader permissions. The workspace catalog used the same unsafe pattern. | Share an atomic writer that creates a randomly named file exclusively with mode `0600`, closes it before replacement, and removes its own temporary file if writing or replacement fails. It never writes into a pre-existing temporary file. |

## Verification

- Before the changes, five new regression cases failed: source and destination carry-over
  junctions, a static-file junction, a linked artifact root, and a credential temporary hard link.
- Regression coverage also checks workspace catalog writes, repeated carry-over, destination
  hard links, temporary-name collisions, and cleanup after a failed atomic replacement.
- Full suite: 187 server tests and 42 web tests pass; one POSIX permission test is skipped on
  Windows. Type checking and the production build pass.
- The first sandboxed full-suite run encountered an agent termination timeout and an HTTP
  connection reset. The HTTP test passed independently, and the complete suite passed when
  rerun with normal Windows process permissions.
- `npm audit --json --ignore-scripts` reports zero known vulnerabilities. No dependency
  updates were needed.

## Compatibility and limits

Carry-over sources must use ordinary files and directories, and new destinations cannot
traverse existing links. Static assets and artifact roots must also be ordinary filesystem
entries. These restrictions can reject an intentionally linked layout that worked previously.

Checks cover the named roots and their descendants. They do not isolate a hostile process
running as the same OS account, prevent concurrent filesystem replacement, or validate every
ancestor of a configured root. Exclusive temporary creation protects against reusing an
existing file; Windows file access remains governed by inherited ACLs, not POSIX mode bits.
Connection credentials remain plaintext on disk. The existing OS-account trust model and
loopback-only deployment requirement still apply.
