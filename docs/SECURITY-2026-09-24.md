# Security review and fixes — 2026-09-24

Reviewed baseline commit `e8e28de30b508214f3de3e6be1dd98ad12922adb` and the resulting working-tree fixes. The application is a local, single-user workflow runner that intentionally executes commands and coding agents. Severity below assumes this deployment model, not an Internet-facing or multi-tenant service.

## Findings addressed

| Finding | Risk and prerequisite | Fix |
| --- | --- | --- |
| Shell template injection — high | A workflow using `{{task.title}}`, description, artifact text, or action output inside its command treated that data as shell source. A crafted title could execute an additional command with the user's OS permissions. This requires a workflow using command interpolation; the supplied default shell commands do not use it. | Reject command template expressions both when saving a workflow and before rendering stored runs or retry overrides. Keep task data in `WM_*` environment variables. |
| Artifact containment bypass — medium | A symlink or Windows junction planted in the artifact directory could make an apparently contained name read or overwrite a file outside it. Requires the ability to place a link there, for example through a prior agent or shell action. | `resolveInside` checks the artifact root and existing descendant components with `lstat`, rejecting links, including dangling links. The shared check covers artifact downloads, template reads, write-artifact actions, and saved agent results. |
| Unsafe integration transport — medium | Jira accepted explicit HTTP URLs and sent the Basic authentication credential without TLS. Unsupported schemes were interpreted as hostnames; embedded URL credentials were silently discarded. Integration requests also followed redirects, potentially forwarding private POST bodies. | Require HTTPS and reject embedded credentials when saving and when constructing the Jira client, including existing stored connections. Refuse integration redirects. Bare hostnames still default to HTTPS. |
| Vulnerable development dependency — moderate advisory | `drizzle-kit` pulled in esbuild 0.18.20 through `@esbuild-kit/core-utils`. The advisory affects esbuild's development server; no use of that vulnerable serve API was found in this app's configured runtime. | Override this dependency to patched esbuild 0.25.12 and update the lockfile. Move drizzle-kit to the workspace root so the installed npm version actually applies the override. The server's existing database command still resolves it. |

The esbuild finding is one underlying advisory, not four independent vulnerabilities: npm initially reported four affected nodes in its dependency chain. The maintainer describes the affected feature and patched range in [GHSA-67mh-4wv8-2f99](https://github.com/evanw/esbuild/security/advisories/GHSA-67mh-4wv8-2f99). The workspace override behavior is also tracked in [npm/cli issue 9659](https://github.com/npm/cli/issues/9659).

Additional protection: the common HTTP guard now caps request bodies at 2 MiB and sends `frame-ancestors 'none'`, `X-Frame-Options: DENY`, `nosniff`, and a no-referrer policy. These apply to workspace catalog routes, forwarded workspace routes, MCP, and the production web app. Rejected oversized HTTP/1 requests close the connection so unread bodies cannot interfere with its next use.

## Verification

- Added regression tests for command validation, saved snapshots and retry overrides, hostile text passed safely through environment variables, junction-based artifact reads and writes, unsafe Jira URLs, connection saves, and redirect policy.
- Before fixes, seven security regression cases failed, including a shell run that succeeded with injected command text and an artifact request returning HTTP 200 through a junction. The tests pass after the fixes.
- Added real loopback HTTP coverage through the complete workspace router: health response and headers, cross-site origin rejection, hostile Host rejection, oversized request rejection, normal workspace creation afterward, and insecure connection rejection without persistence.
- Complete suite: 178 server tests and 42 web tests pass. Type checking and production build pass.
- `npm audit --json --ignore-scripts`: zero reported vulnerabilities after the dependency fix. `npm ls esbuild --all` resolves the intended versions without invalid dependency edges; `npm ci --dry-run --ignore-scripts --no-audit --no-fund` accepts the lockfile.
- `npm exec -w server -- drizzle-kit check` passes. Also verified a TypeScript transformation through the affected esbuild wrapper.
- A targeted scan of 205 tracked text files found no private-key blocks or matches for the selected AWS, GitHub, and OpenAI token formats. This was not a complete secret-history audit.
- Tests used temporary databases, synthetic files, and dummy credentials. No production workspaces, live integration writes, or real agent sessions were used. The pre-existing `.claude/launch.json` change was left untouched.

The initial baseline run hit a Windows process-termination timeout in the sandbox. Running the agent tests and the complete suite with normal OS process access passed. Direct TypeScript-loader and database-tool checks also required normal Windows user-information access.

## Migration

Saved shell commands containing `{{...}}` now fail with an explanatory error. Replace interpolation with a script that reads environment variables as data. PowerShell example: `Write-Output $env:WM_TASK_TITLE`. Bash example: `printf '%s\n' "$WM_TASK_TITLE"`. For cmd.exe, prefer a script reading `process.env.WM_TASK_TITLE` instead of expanding task text into cmd syntax. Do not use `eval`, `Invoke-Expression`, or a second shell interpretation of these values.

Existing HTTP Jira connections must be changed to HTTPS before they can be tested or used. Configure the final API host directly because redirects are refused. Artifact paths that intentionally used symlinks or junctions must use ordinary files and directories instead.

## Trust boundary and limits

The listener remains loopback-only with Host and Origin validation. SQL queries use Drizzle bindings, task identifiers are generated, artifact downloads are plain text with `nosniff`, Markdown uses the renderer's default HTML/URL protections, and per-run MCP tokens expire with their runs. Existing tests cover these paths and workspace separation.

Local HTTP clients are intentionally unauthenticated. Autonomous agent adapters can disable their CLI sandbox/approval controls and run under the same OS account as the app. Such a process can call the approval API, read local credentials, or change the database directly. Workspaces and human approval steps therefore are **not a security boundary against hostile local processes**. A browser token alone would not isolate a process that can read the server's files. Running untrusted agents requires a separately enforced OS/container/VM boundary with controlled filesystem and network access; this change does not introduce that architecture.

The artifact checks reject existing links; they are not an OS sandbox and cannot prevent a malicious same-account process from racing filesystem operations or replacing an ancestor directory. Connection secrets remain plaintext on disk, protected by filesystem access controls. Transcript and task content can contain sensitive data independently of the separate connection-secret store.

The review covered request handling, workflow/run execution, MCP, filesystem access, Git/process invocation, integration clients, credential storage, UI rendering, configuration, and the dependency tree. It did not include a live browser attack campaign, external account penetration tests, exhaustive fuzzing, Git-history secret scanning, or validation of every installed third-party agent CLI's sandbox behavior.
