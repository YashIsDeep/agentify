## Confirmed findings

### QA-01 — P1: Incomplete feedback-field change breaks task operations

**Reproduce:** Start the current server against the QA database and open any board. Alternatively, call `GET /api/tasks`. New-database test harnesses also fail when creating tasks.

**Actual:** Board shows `Could not load tasks: Internal server error`; the endpoint returns HTTP 500. Server logs report `no such column: "feedback"`. Task creation in the tests reports `table tasks has no column named feedback`.

**Cause:** [schema.ts](C:/code/workflow-manager/server/src/db/schema.ts:89) declares a required JSON `feedback` field. Migration history ends at `0009_agent_approval` and still creates `last_feedback`; no migration creates `feedback`. The engine and runner still reference `lastFeedback`, and the shared task type still requires it. Type errors occur at engine.ts lines 530, 568, and 1063, and runner.ts line 175.

**Impact:** Boards, task details, task creation, archive loading, and dependent action flows cannot be accepted on the current version. Fresh database tests show this is not limited to upgrading the older QA database.

**Recommended fix:** Complete the feedback model consistently across migrations, engine, runner, and shared types. Preserve existing feedback according to the intended migration behavior. Validate both an upgraded database and a fresh database; then rerun the full suite and browser task lifecycle.

### QA-02 — P2: Browser Back silently discards unsaved workflow edits

**Reproduce:** Navigate from a board to Workflows. Expand Name & description. Enter a new description without saving and verify `Unsaved changes`. Press browser Back, then Forward.

**Actual:** Back leaves the editor without a confirmation. Forward reopens the editor with the description blank and `All changes saved`. The unsaved text is lost.

**Expected:** Preserve the draft or ask before discarding it, including browser history navigation.

**Cause:** [url-state.ts](C:/code/workflow-manager/web/src/lib/url-state.ts:7) handles `popstate` by notifying subscribers directly. The unsaved-change guards only run in `setQueryParams`; same-document browser Back/Forward does not use that function or trigger `beforeunload`.

**Recommended fix:** Cover browser history navigation with draft preservation or a consistent navigation guard. Add a browser regression covering Back, Forward, cancellation, and restored draft contents. The same shared mechanism is used by task-detail edits, which need retesting after QA-01 is fixed.

### QA-03 — P2: Closed mobile sidebar remains keyboard-focusable

**Reproduce:** At 390×844, open Agents with navigation closed. Focus `Open navigation` and press Tab.

**Actual:** Focus moves to the invisible `Workflow Manager` button in the off-screen sidebar. Its measured bounds were x=-202 through x=-14.67. Hidden navigation controls also remain in the accessibility tree.

**Expected:** Closed navigation should not participate in keyboard navigation or be exposed as usable content to assistive technology. Tab should move to visible page content.

**Cause:** [Sidebar.tsx](C:/code/workflow-manager/web/src/components/Sidebar.tsx:56) always renders the interactive sidebar; [styles.css](C:/code/workflow-manager/web/src/styles.css:3616) only moves it off-screen with a transform.

**Recommended fix:** Make the closed sidebar inert/hidden at the mobile breakpoint, restore interaction when opened, and verify focus restoration on close. Keep desktop navigation available.

### QA-04 — P2: Archive reports an empty archive after a failed request

**Reproduce:** Open Archive while its task request returns HTTP 500 (currently reproducible through QA-01).

**Actual:** The page displays `Internal server error` and `Nothing archived yet` together. It claims there are no archived tasks even though it could not retrieve them.

**Expected:** Show a failure state with a retry action; show the empty state only after a successful empty response.

**Cause:** [ArchiveView.tsx](C:/code/workflow-manager/web/src/components/ArchiveView.tsx:53) checks the error and empty conditions independently. Undefined data becomes an empty list, and `!tasks.isLoading` also holds after failure.

**Recommended fix:** Make loading, error, empty, and populated states mutually exclusive. Add a request-failure UI check so this remains correct after the database issue is fixed.
